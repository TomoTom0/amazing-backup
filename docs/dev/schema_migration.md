# 保存形式の互換性と移行の設計

0.2.0 移行方式の見直し設計（TASK-26）。現行の「schema 一斉繰り上げ＋初期化（reset）と再 push」という移行方式を廃止し、後継の互換・移行の扱いを確定させるための設計資料である。

**本書の確定部分と未確定部分**: 2章（現行方式の問題点）と 3章（移行方式の確定部分: reset+再 push の除外・本体不変・移行対象はメタデータ層のみ）は確定した設計判断である。**4章（読取互換を保持するか、保持する場合の範囲と期限）は未確定であり、選択肢 A/B/C の比較資料として提示する**。選択は本人の判断事項であり、選択まで実装の起票は行わない（repo の CLAUDE.md のルール: 後戻りコストが大きい設計決定はユーザーの承認を得てから進める）。

経緯:

- 2026-11-22 本人の判断（判断事項チャット経由）: メタデータの変更で既存データの完全置換が必要になる前提はおかしい。本体は追加型・不変が前提のはずで、メタデータも頻繁に置換するものではない。reset＋再 push 方式での移行としては進めず、移行設計そのものの見直しを要する。
- 2026-11-24 本人の訂正（判断事項チャット経由）: 「互換を残し続けると言った記憶はない」。2026-11-22 の見解は完全置換・頻繁な置換の前提への異議であって、読取互換の維持の指示ではない。互換の扱いは設計側の責任で再提示する。再提示があるまで互換の扱いは未確定として扱い、実装範囲の起票も行わない。

本版（v2・2026-11-24）はこの再提示である。初版（v1・2026-11-22）は「読取互換を既定とする」構成であったが、これは設計側の推奨案の提示であって本人の意向の確認ではない。本版では互換の扱いを 4章の選択肢比較として再構成した。

## 1. 原則

- **P1 本体不変**（本人の 2026-11-22 の判断に由来）: 本体データ（`data/<uuid>/…`）は追加型・不変である。メタデータの変更・移行は、本体の再アップロード・削除・移動を決して要求しない。
- **P2 移行は例外**（本人の 2026-11-22 の判断に由来）: 保存形式の移行は通常運用ではなく例外事象である。語彙（field 名）の変更程度では移行が発生しない構造にする。
- **P3 移行はメタデータのみ・可逆・低コスト**（設計側の原則。P1・P2 から導出）: やむを得ず移行を行う場合も、対象はメタデータに限定し、原本を保全したまま変換でき、失敗時に切り戻せる形にする。全量置換型の移行は採らない。
- **P4 履歴は書き換えない**（設計側の原則。manifest の不変履歴という実装の性質に由来）: registry・manifest のような追記型の記録は、過去分を書き換えない。世代の混在は許容し、扱いは読取側または変換コマンドで決める（4章）。

移行手順のレビューでは「本体に触れる段が含まれていないこと」を確認項目とする。

## 2. 現行方式の問題点（実測に基づく）

### 2.1 問題の所在の切り分け

本体層に問題はない。実体は発行 UUIDv7 キー（`data/<uuid>/default.age`）で管理され、ファイルの移動・改名で実体が動かない構造は既に成立している。問題は次の3つのメタデータ形式に限られる。

| 形式 | 置き場所 | 性質 |
|---|---|---|
| 索引 | S3 単一 object（STANDARD・hot） | registry から全再構築して PUT する経路が通常運用に既にある |
| registry | ローカル file（`registry.jsonl`・追記型） | 全操作の真正。端末ローカルに存在する |
| manifest | S3 `sys/manifests/`（prod は DEEP_ARCHIVE） | run 単位の監査記録。追記型の履歴 |

### 2.2 語彙改名を schema 版数の一斉繰り上げで処理した

0.2.0 の変更の実体は、JSON の field 名の変更（`rel_path` → `label`）である。これは serde の alias で読取互換が取れる変更であり、保存形式の構造変更ではない。ところが現行設計は、索引 schema 2→3・registry file_write record schema 2→3・manifest file record schema 2→3 の一斉繰り上げに、厳格な拒否（索引 header の版数照合、`deny_unknown_fields`、index rebuild 時の旧 record 検査）を組み合わせたため、保存済みの全データが新 binary で読めなくなった。

実態として、record 種別ごとの版数の混在（metadata schema=1、manifest batch header=2、file_upload record schema=2 等）は既に通常の状態であり、「形式全体の一斉繰り上げ」という発想自体が実態に合っていない。版数を「語彙の版数」として使ったことが、改名のたびに移行イベントを発生させる構造を作った。

### 2.3 「初期化で消えるから互換層は不要」という前提

`src/registry.rs` の冒頭には「dev 初期化で registry ごと消えるため互換層は不要」という設計前提が明記されている。dev bucket の初期化という開発都合を、prod を含む全環境の保存形式設計の前提にしたことが誤りの出発点である。prod では `manage reset` 自体が purpose=dev 限定で実行できず、結果として prod には移行手段が存在しないまま、「reset＋再 push」が唯一の移行手順として changelog と使用手順書に文書化された。

### 2.4 拒否が一律で、回復経路が全量再構築しかない

- registry は旧形式の行が1行あるだけで load 全体が失敗する（行単位の parse 失敗が全体のエラーになる）。
- 索引は header の版数1値で全体が読めなくなる。
- manifest は旧 record が1件あるだけで index rebuild 全体が失敗する（TASK-22 で入った一律失敗の検査）。

いずれも「読める範囲を読み、旧形式を変換して取り込む」という中間がなく、回復は全量の作り直し（初期化と再 push）しか残されていない。

### 2.5 reset＋再 push の実コストとリスク（prod・DEEP_ARCHIVE）

- reset は prefix 配下の全 version・delete marker を恒久削除する。本体も例外ではない。DEEP_ARCHIVE には最低保存期間（180日）があり、期間内の削除は残期間分の保存料が按分課金される（早期削除）。再投入した本体は最低保存期間の時計が再び始まる。
- 再 push は全本体の再暗号化・再アップロードである。PUT の件数課金自体は本体が大きな file であるため支配的ではないが、次の2点が構造的な問題である。
  - 原データ（source file）がローカルに残っていない本体は再 push できず、reset の時点で唯一の複製が失われる。バックアップの移行手順が「原データの現存」を前提にすることは、バックアップの目的と矛盾する。
  - S3 側から戻す場合は取得料（DEEP_ARCHIVE の取得は Standard で $0.02/GB・Bulk で $0.0025/GB が米国東部の単価。東京リージョンはこれより高い）と、最大48時間の復元待ちがかかる。
- 費用の総額は bucket の総量・件数に比例する。本人の実運用 config（bucket 実名・object 件数・総量）は本設計作業の到達範囲からは未確認であり、総額の断定はしない。ただし「語彙改名1回ごとに全量置換」という比例関係自体が誤りであり、総量が増えるほど破綻する構造であることが問題である。

### 2.6 表層の変更と保存形式の破壊を束ねた

config の key 改名（`[files].path` → `label`）と CLI flag 改名（`--path` → `--source-path`）は、ローカル・表層の変更であり保存データとは無関係である。これらと保存形式の破壊を同じ「0.2.0 破壊的変更」に束ねたため、表層の都合で保存データの移行が要るかのような構造になった。変更の影響範囲は層ごとに分けて扱うべきである。

## 3. 移行方式の確定部分（全案共通）

### 3.1 除外される方式

- **reset＋再 push**: 本人の 2026-11-22 の判断により移行手順から除外する。reset は dev 初期化専用の道具へ戻し（purpose=dev gate は現行実装のまま）、changelog と使用手順書から移行手順としての記述を外す。
- **S3 上の manifest を書き換える一括変換**: manifest は DEEP_ARCHIVE 上の不変履歴であり、書き換えは取得（費用＋最大48時間の復元待ち）と再アップロードを伴う履歴の改変になる（P4 違反）。対象から除外する。
- **二重書込（移行期間中に旧新両形式を書き分ける）**: 単一利用者の道具に対して過剰な機構である。対象から除外する。

残る機構は「読取互換（読取側で旧形式を受理する）」と「ローカル変換（ローカルにあるデータを現行形式へ寄せる）」の2系統である。この2系統は排他ではなく、層ごと・期間ごとに組み合わせられる。4章の各案の違いはこの組合せの違いである。

### 3.2 層の性質と使える機構（実測）

| 層 | 性質（実測） | 読取互換 | ローカル変換 |
|---|---|---|---|
| 本体 | 発行 UUID キーで追加型・不変。rename/location と無関係 | 使わない（全案で本体に触れない） | 使わない |
| registry | 端末ローカルの追記型 JSONL。全操作の真正 | alias で旧行を読み続けられる | ローカルで完結（退避＋行単位書換・可逆）。S3 費用 0 |
| 索引 | S3 単一 object（STANDARD）。registry からの全再構築＋PUT が通常書込経路として既に存在（backup push・prune・reconcile・location-rm の各経路） | 旧索引の互換 parse が必要な期間は binary 更新〜次の書込まで（次の書込で現行形式へ自動置換） | 「変換」は存在しない（再構築で自動的に現行形式になる）。再構築の正規の起点は registry |
| manifest | S3 `sys/manifests/`（prod は DEEP_ARCHIVE）・run 単位の不変履歴。読むのは index rebuild（災害復旧）のみ。parse は Value 層で読取時変換は技術的に容易 | 読取時変換が可能（対象は index rebuild のみ） | **構造的に存在しない**（書換・再アップロードは P4 違反・取得費用） |

実測上の補足:

- 明示的に索引を再構築するコマンドは現状 manifest 起点の `manage index rebuild` のみで、registry 起点の明示コマンドは無い（`manage index reconcile` は旧索引の読取を前提に動く）。registry 起点の再構築は書込経路の部品（build_entries＋upload_index）としては存在するため、案によってはこの部品を露出させる整備を要る（6章）。
- registry が旧形式の行で load できない間は書込経路全体が動かない（build_entries は registry の load を前提とする）。このため「次の書込で索引が自動置換する」は、registry が読める状態（互換 or 変換済み）になってからの話である。
- catalog DB（ローカル）は派生データで `manage catalog rebuild` により常に再構築できるため、互換・変換のいずれの案でも対象外とする。

## 4. 読取互換の扱いの選択肢（未確定・本人の判断事項）

### 4.1 問いと選択肢の定義

問い: 過去形式の保存データ（registry の旧行・旧索引・manifest の旧 file record）を、新 binary の読取側は受理し続けるか。0.2.0 で具体的には、`rel_path`（旧）→ `label`（新）の語彙改名と schema 2→3 の版数の組をどう扱うか。

- **案A 無期限保持（indefinite keep）**: 読取側は過去形式を恒久的に受理する。alias と版数 adapter を蓄積し、保存形式 fixture テスト（5章）で恒常的に保証する。保存データは一切書き換わらない。
- **案B 期限・範囲付き保持（bounded keep）**: 受理可能な版数の集合と、期限（版数・日付等）または範囲（層ごと）を区切って保持する。期限内は案A と同じ読取。期限後に旧形式へ当たった場合は明確なエラーと変換コマンドの案内に変わる。
- **案C 保持しない＋非破壊変換（not keep with non-reset alternative）**: 読取側は現行版数のみ受理する。旧形式の保存データは変換コマンドで現行形式へ寄せる。変換は reset に依存しない非破壊手段（ローカル・原本保全・可逆）として提供する（3.1 のとおり S3 上の manifest を書き換える方式は含まない）。

### 4.2 層別の帰結

| 層 | 案A | 案B | 案C |
|---|---|---|---|
| 本体 | 触れない（全案共通・P1） | 同左 | 同左 |
| registry（ローカル） | 旧行を alias で読み続ける。変換不要 | 期限内は alias 読取。期限後はローカル変換（退避付き・可逆） | 変換コマンドで一括変換（退避付き・可逆）。以後の reader は現行のみ |
| 索引（S3・STANDARD） | binary 更新〜次の書込までの照会は互換 parse。次の書込で現行形式へ自動置換 | 同左。期限切れ・長期間書込がない場合は registry 起点の明示再構築で現行化 | 索引自体の変換は不要。registry 変換後に再構築（通常書込または明示再構築）で現行形式になる |
| manifest（DEEP_ARCHIVE・不変履歴） | 旧 record を読取時変換で受理。災害復旧（index rebuild）は全 run が対象 | **期限を付けると期限経過後に旧 manifest が読めなくなる**（書換不能なため期限後に「寄せる」手段が存在しない）。案Bを採るなら manifest のみ無期限（案A と同じ扱い）が実質 | 旧 manifest は新 binary では読めない。災害復旧は変換後の run が対象。旧 manifest を読み続けるには manifest のみ alias 例外（案A の部分採用）が必要 |

### 4.3 比較表

| 観点 | 案A 無期限保持 | 案B 期限・範囲付き | 案C 保持しない＋非破壊変換 |
|---|---|---|---|
| 0.2.0 適用時の各環境の作業 | binary 更新のみ | 期限内なら binary 更新のみ | binary 更新＋変換コマンド 1回（ローカル） |
| 移行イベント | なし | 期限経過時に、旧データの残る環境で 1回 | 形式を変えるたびに各環境 1回 |
| S3 操作・費用 | なし | なし（索引 PUT は通常書込と同一操作） | 索引 PUT 1件（通常書込と同一操作）。DEEP_ARCHIVE 取得・本体操作なし |
| 読取側の複雑さ | 版数 adapter・alias の蓄積（語彙改名は alias で軽い） | 期限内は案A と同等＋受理版数集合・期限の管理・deprecation 警告 | 常に現行のみで最小 |
| 変換コマンドの整備 | 不要 | 期限後向けに必要 | 恒久資産として必要（版数の組ごと） |
| manifest の災害復旧 | 全 run | 無期限扱いなら全 run。期限を付ければ旧 run 喪失 | 変換後 run のみ（manifest の alias 例外を入れれば全 run） |
| 将来の語彙改名時 | alias 追加のみで再発なし | 期限内は同左。期限後は変換イベント | 版数 up＋変換の組で提供（5章）。変換イベントが再発 |
| 未確認要素への依存 | なし（総量・件数に非依存） | 期限の設定根拠（総量・件数・頻度の実績値が必要だが未確認） | なし |

### 4.4 設計側の評価

設計側の分析であり、本人の意向の表明ではない。

1. 3案の差が実質的に効くのは registry と manifest の2層に集約される。索引はどの案でも次の書込で現行形式へ置き換わり（3.2）、本体は無関係である。
2. registry 層では、案A（alias の実装）と案C（変換コマンドの実装＋各環境 1回の実行）のいずれもローカル完結の小規模な作業であり、費用・リスクの差は小さい。
3. 案Bは、期限内の読取（案A と同じ reader）と期限後の変換（案C と同じコマンド）の両方を整備することになる。単一利用者の道具では「binary 更新と変換実行の間に grace 期間を置く」便益が小さく、整備面では両案の内容を合わせ持つ中間となる。
4. manifest 層は書換不能なため「変換して寄せる」が存在せず（3.2）、扱いは実質的に「読み続ける（alias）」か「読まなくなる（災害復旧の対象が変換後の run に限定）」の二値になる。案Bの期限はこの層に適用できず、案Cを選んでも manifest だけ alias を残す構成（案A の部分採用）が可能で、その費用は Value 層の読取時変換 1か所と小さい。
5. 案Aの恒久維持コスト（版数 adapter・fixture の蓄積）は形式変更の頻度に比例する。語彙改名は alias、構造変更は稀（5章の運用規則）とすれば蓄積速度は遅い。案Cの恒久維持コスト（変換コマンドの版数の組ごとの整備）も同じく頻度に比例する。
6. まとめ: 実測の上では費用・リスクの差は小さく、選択の本質は「保存形式を変える時、過去の保存データに対する読取の保証をどこまで続けるか」というポリシーである。整備の重さの軸では案Bが最も重く（案A＋案C の整備を要する）、その便益（grace 期間）は単一利用者の運用では小さい。

### 4.5 判断の要点

1. 旧形式の保存データを新 binary が読み続けることを永続的に保証するか（案A）、保証せず変換で対応するか（案C）。案Bは中間だが、4.4-3 のとおり整備は両案分であり、grace 期間の便益が小さい。
2. 案C（または案Bの期限経過後）を選ぶ場合、manifest の旧 run の扱いを決める: (i) manifest のみ alias を残して災害復旧は全 run を維持する、(ii) 災害復旧は変換後の run に限定することを明示的に受け入れる。
3. 想定する形式変更の頻度: 語彙改名が主で構造変更が稀であれば、案Aの蓄積も案Cの変換イベントも稀にしか発生しない。頻繁な構造変更を想定するなら、いずれの案でも 2.2 と同じ過ち（版数の濫用）を避ける運用規則（5章）が前提になる。

## 5. schema 版数の運用規則（案別の差分を含む）

全案で共通の規則:

- 版数は record 種別ごとの「構造版数」として使う（実態は既に record 種別ごとの混在: metadata schema=1、manifest batch header=2、file_upload record schema=2 等）。形式全体の一斉繰り上げはしない（2.2 の過ち）。
- 読取の失敗は当該 record・header 単位に閉じ込める（2.4 の解消）。行単位の失敗で registry 全体・索引全体を巻き込まない。エラー文には当該版数と、対応手段（旧版 adapter または変換コマンドの有無）を示す。
- 保存形式 fixture テストを恒常化する: 過去版数の実サンプルを tests に保持し、merge 条件とする。条件は案別: 案A・案Bは「新 binary が全 fixture を読めること」、案Cは「変換コマンドが全 fixture を現行形式へ変換できること」。

案別の規則:

- **案A**: field の改名=alias を追加し、版数は上げない。field の追加=default 付きで追加し、版数は上げない。field の意味・型・構造の変更=版数を上げ、旧版の reader adapter を恒久維持する。未知の版数=当該 record 単位の失敗。
- **案B**: 案A と同じ変更規則に加え、受理版数の集合と期限を文書で宣言する。期限切れの版数は deprecation 警告を経て集合から外す。集合から外す PR は、変換コマンドが当該版数を処理できることを条件とする。
- **案C**: 非互換変更（field の改名を含む）は版数を上げて提供する（旧形式の判定を版数で一意にするため）。reader は常に現行版のみ受理する。版数を上げる PR は変換コマンドの更新をセットとする。

## 6. 各案の 0.2.0 への適用と実装範囲

共通（全案）:

- 移行手順に reset を含めない。changelog（unreleased）の移行手順と usage_backup.md の該当節、`src/registry.rs` 冒頭の前提コメント（「dev 初期化で registry ごと消えるため互換層は不要」）の書換は、選択後の実装として行う。
- エラー文の「初期化と再 push が必要」系の案内（manifest 検査等）は全案で書換対象になる（案A・案Bは互換 parse への案内、案Cは変換コマンドへの案内）。
- 表層（config 旧 key `[files].path`・CLI 旧 flag `--path`）の経過措置は保存データとは別軸の配慮として推奨する（必須ではない）: 受理して警告する、または移行先を示すエラーにする。

### 6.1 案Aの適用と実装範囲

- 実装範囲: file_write record・索引 entry・manifest file record の 3か所に `rel_path` の alias を入れ、schema 2・3 の双方を受理する。索引 header と manifest の版数検査を「受理版数の集合＋読取時変換」へ改める。TASK-22 の一律失敗の検査を「変換不能な record のみ失敗」へ改める。旧版 fixture の整備と条件書への恒常条件の追加。共通の文書書換。
- 適用: dev・prod とも binary 更新のみ。索引は次の書込で現行形式へ置換し、それまでの照会は互換 parse で継続する。registry の旧行はそのまま残り alias で読まれる。
- 適用後の確認: 旧データに対する照会系（list / query / get）と新規 push の追加が動くこと。データの作り直しは確認項目に含めない。

### 6.2 案Bの適用と実装範囲

- 実装範囲: 案Aの reader 変更に加え、受理版数の集合と期限の宣言（文書＋code 内定数）・期限切れ版数への deprecation 警告・期限後向けの変換コマンド（案C と同じもの）。
- 適用: 期限内なら binary 更新のみ。期限経過後に旧データが残る環境では変換コマンドを 1回実行する。manifest への期限は適用しない（4.2・4.4-4）。

### 6.3 案Cの適用と実装範囲

- 実装範囲: 変換コマンドの新設（manage サブコマンドを想定）。構成: (1) registry の変換: file_write 行の schema 2→3・`rel_path`→`label` の書換（旧行の退避は reset の退避流儀と同じ ./tmp/ 配下・dry-run・原本保全・失敗時の切り戻し）。(2) 索引の再構築: build_entries＋upload_index（通常書込経路と同一の部品。索引自体の変換は不要）。(3) catalog rebuild の案内。manifest は変換しない。旧 manifest の扱い（4.5-2 の (i)/(ii)）は案C内の追加判断。
- 適用: binary 更新＋各環境で変換 1回。S3 操作は索引 PUT 1件（通常書込と同一操作）。DEEP_ARCHIVE の取得・本体の操作は一切発生しない。
- 適用後の確認: 変換後の registry で照会系と新規 push が動くこと。退避 file からの切り戻し（dry-run を含む）。
