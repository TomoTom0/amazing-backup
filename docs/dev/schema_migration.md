# 保存形式の互換性と移行の設計

0.2.0 移行方式の見直し設計（TASK-26）。現行の「schema 一斉繰り上げ＋初期化（reset）と再 push」という移行方式を廃し、保存形式の後方互換を読取側の責務とする方式へ改めるための設計判断を記録する。本書は恒久的に保守される設計文書であり、実装は本書のレビュー承認後に別途行う（repo の CLAUDE.md のルール: 後戻りコストが大きい設計決定はユーザーの承認を得てから進める）。

起点は 2026-11-22 の本人の判断である: メタデータの変更で既存データの完全置換が必要になる前提がおかしい。本体は追加型・不変が前提のはずで、メタデータも頻繁に置換するものではない。メタデータの移行自体は禁止しないが、頻繁に行う前提の設計はおかしい。

## 1. 原則

- **P1 本体不変**: 本体データ（`data/<uuid>/…`）は追加型・不変である。メタデータの変更・移行は、本体の再アップロード・削除・移動を決して要求しない。移行手順のレビューでは「本体に触れる段が含まれていないこと」を確認項目とする。
- **P2 移行は例外**: 保存形式の移行は通常運用ではなく例外事象である。語彙（field 名）の変更程度では移行が発生しない構造にする。
- **P3 移行はメタデータのみ・可逆・低コスト**: やむを得ず移行を行う場合も、対象はメタデータに限定し、原本を保全したまま変換でき、失敗時に切り戻せる形にする。全量置換型の移行は採らない。
- **P4 履歴は書き換えない**: registry・manifest のような追記型の記録は、過去分を書き換えず、世代の混在を読取側の互換で吸収する。

## 2. 現行方式の問題点（実測に基づく）

### 2.1 問題の所在の切り分け

本体層に問題はない。実体は発行 UUIDv7 キー（`data/<uuid>/default.age`）で管理され、ファイルの移動・改名で実体が動かない構造は既に成立している。問題は次の3つのメタデータ形式に限られる。

| 形式 | 置き場所 | 性質 |
|---|---|---|
| 索引 | S3 単一 object（STANDARD・hot） | registry から全再構築して PUT する経路が通常運用に既にある |
| registry | ローカル file（`registry.jsonl`・追記型） | 全操作の真正。端末ローカルに存在する |
| manifest | S3 `sys/manifests/`（prod は DEEP_ARCHIVE） | run 単位の監査記録。追記型の履歴 |

### 2.2 語彙改名を schema 版数の一斉繰り上げで処理した

0.2.0 の変更の実体は、JSON の field 名の変更（`rel_path` → `label`）である。これは serde の alias で読取互換が取れる変更であり、保存形式の構造変更ではない。ところが現行設計は、索引 schema 2→3・registry file_write record schema 2→3・manifest file record schema 2→3 の一斉繰り上げに、厳格な拒否（索引 header の版数照合、`deny_unknown_fields`、index rebuild 時の旧 record 検査）を組み合わせたため、保存済みの全データが新 binary で読めなくなった。

実態として、record 種別ごとの版数の混在（metadata schema=1、manifest batch header=2、file_upload record schema=2 等）は既に通常の状態であり、「形式全体の一斉繰り上げ」という発想自体が実態に合っていない。版数を「語彙の版数」として使ったことが、改名のたびに移行イベントを発生させる構造を作った。

### 2.3 「初期化で消えるから互換層は不要」という前提

`src/registry.rs` の冒頭には「dev 初期化で registry ごと消えるため互換層は不要」という設計前提が明記されている。dev bucket の初期化という開発都合を、prod を含む全環境の保存形式設計の前提にしたことが誤りの出発点である。prod では `manage reset` 自体が purpose=dev 限定で実行できず、結果として prod には移行手段が存在しないまま、「reset＋再 push」が唯一の移行手順として changelog と使用手順書に文書化された。

### 2.4 拒否が一律で、回復経路が全量再構築しかない

- registry は旧形式の行が1行あるだけで load 全体が失敗する（行単位の parse 失敗が全体のエラーになる）。
- 索引は header の版数1値で全体が読めなくなる。
- manifest は旧 record が1件あるだけで index rebuild 全体が失敗する（TASK-22 で入った一律失敗の検査）。

いずれも「読める範囲を読み、旧形式を変換して取り込む」という中間がなく、回復は全量の作り直し（初期化と再 push）しか残されていない。

### 2.5 reset＋再 push の実コストとリスク（prod・DEEP_ARCHIVE）

- reset は prefix 配下の全 version・delete marker を恒久削除する。本体も例外ではない。DEEP_ARCHIVE には最低保存期間（180日）があり、期間内の削除は残期間分の保存料が按分課金される（早期削除）。再投入した本体は最低保存期間の時計が再び始まる。
- 再 push は全本体の再暗号化・再アップロードである。PUT の件数課金自体は本体が大きな file であるため支配的ではないが、次の2点が構造的な問題である。
  - 原アーカイブがローカルに残っていない本体は再 push できず、reset の時点で唯一の複製が失われる。バックアップの移行手順が「原データの現存」を前提にすることは、バックアップの目的と矛盾する。
  - S3 側から戻す場合は取得料（DEEP_ARCHIVE の取得は Standard で $0.02/GB・Bulk で $0.0025/GB が米国東部の単価。東京リージョンはこれより高い）と、最大48時間の復元待ちがかかる。
- 費用の総額は bucket の総量・件数に比例する。本人の実運用 config（bucket 実名・object 件数・総量）は本設計作業の到達範囲からは未確認であり、総額の断定はしない。ただし「語彙改名1回ごとに全量置換」という比例関係自体が誤りであり、総量が増えるほど破綻する構造であることが問題である。

### 2.6 表層の変更と保存形式の破壊を束ねた

config の key 改名（`[files].path` → `label`）と CLI flag 改名（`--path` → `--source-path`）は、ローカル・表層の変更であり保存データとは無関係である。これらと保存形式の破壊を同じ「0.2.0 破壊的変更」に束ねたため、表層の都合で保存データの移行が要るかのような構造になった。変更の影響範囲は層ごとに分けて扱うべきである。

## 3. 見直し設計

### 3.1 方針: 読取互換を既定とし、移行イベントを消す

- 書込は現行形式のみ。読取は過去形式を全て受理する。後方互換は読取側の責務とする。
- field の改名は serde alias（旧名を受理し、内部表現へ正規化）で吸収し、schema 版数を上げない。
- schema 版数を上げるのは、field の意味・型・構造が変わり alias では吸収できない場合に限る。その場合も版数ごとの reader adapter を用意し、旧版の読取を恒久的に維持する。

### 3.2 形式ごとの扱い

#### (a) registry（ローカル追記型 JSONL）

- file_write record は `label` を正名とし、`rel_path` を alias として受理する。schema 値は 2・3 の双方を受理し、内部表現へ正規化する。`deny_unknown_fields` は誤字検出のために維持するが、改名した field は alias として列挙する。
- 既存の旧行は書き換えない（P4）。reduce は正規化後の内部表現でのみ行うため、旧行と新行の混在は通常状態として扱える。
- 旧行を新形式へ寄せる一括変換は行わない。どうしても必要な場合に限り、原本バックアップ付き・S3 非干渉のローカル変換コマンドを別途設計する（本書では必須としない）。

#### (b) 索引（S3 単一 object・STANDARD）

- header の版数照合を「現行版との完全一致」から「受理可能な版数の集合」へ改める。entry の field は registry と同じ alias 方針とする。
- 索引は registry からの全再構築（`build_entries` による再構築＋PUT）が通常の書込経路として既に実装されているため、索引だけが旧形式のままでも、次の書込で自動的に現行形式へ置き換わる。読取のみで使い続ける期間は互換 parse で継続できる。
- 明示的に索引を作り直す場合の正規の起点は registry とし、manifest 起点の再構築（現行の `manage index rebuild`）は「ローカル registry を失った場合の災害復旧」へ位置づけ直す。

#### (c) manifest（run 単位・DEEP_ARCHIVE・不変の履歴）

- 過去の manifest は書き換えない・再アップロードしない（P1・P4）。取得（復元）も移行目的では行わない。
- index rebuild の parse は `serde_json::Value` 層で行われているため、旧 record（schema=2・`rel_path` 入り）を読取時に `label` へ変換する adapter を入れる。TASK-22 の一律失敗の検査は、「変換可能な旧 record は変換して取り込み、変換不能な record（label・rel_path の双方が無い等）のみ失敗する」へ改める。
- manifest は run の監査記録であり、形式の世代が混在するのは正常な状態とする。

#### (d) 本体・metadata・pin

- 本体には一切触れない。移行に関するいかなる手順・実装にも、本体の削除・再アップロードの段を含めない。
- metadata（schema=1）は今回無変更であり、将来も本書の方針に従う。

### 3.3 schema 版数の運用規則（将来の変更への耐性）

- 版数は record 種別ごとの「構造版数」と定義し直す。形式全体の一斉繰り上げはしない。
- 変更の種類ごとの扱いを固定する。
  - field の改名: alias を追加する。版数は上げない。
  - field の追加: default 付きで追加する。版数は上げない。
  - field の意味・型・構造の変更: 版数を上げ、旧版の reader adapter を追加する。旧版の読取は恒久的に維持する。
- reader が未知の版数に当たった場合の失敗は、その record（または header）の範囲に閉じ込める。行単位の record の失敗で全体を巻き込まない。エラーメッセージには当該 record の版数と、対応する変換が存在しない旨を示す。
- 保存形式の fixture テストを恒常化する: 過去の全版数の実サンプル（fixture）を tests に保持し、新 binary が全 fixture を読めることを条件書の恒常条件とする。保存形式を変更する PR は fixture の追加とセットでなければならず、旧 fixture の読取が壊れる変更はマージしない。

### 3.4 dev / prod への適用

- dev: binary を 0.2.0 へ上げるだけである。reset は dev 初期化専用の道具へ戻し、移行手順からは外す。
- prod: binary を上げるだけである。本体の取得・削除・再アップロード、DEEP_ARCHIVE の復元は一切発生しない。索引は次回の書込で現行形式へ置き換わり、それまでの照会は互換 parse で継続する。registry の旧行はそのまま残り、読取互換で処理される。
- 適用後の確認項目は、旧データに対する照会系（list / query / get）の動作と、新規 push の追加ができることであり、データの作り直しは確認項目に含めない。

### 3.5 0.2.0 の変更自体を非破壊にする条件（移行が不要になる条件）

次の3点を満たせば、0.2.0 は保存データに対して非破壊となり、いかなる環境でも移行手順なしに適用できる。

1. file_write record・索引 entry・manifest file record の読取に `rel_path` の alias を入れ、schema 2・3 の双方を受理する。
2. 索引 header・manifest record の版数検査を「受理可能な版数の集合＋読取時変換」へ改める。
3. changelog と使用手順書の移行手順（reset＋再 push）を「移行不要（binary の更新のみ）」へ書き換え、`src/registry.rs` 冒頭の「互換層は不要」という前提コメントを本書への参照に置き換える。

加えて、保存データとは別軸の配慮として次を推奨する（必須ではない）: config の旧 key（`[files].path`）は即座に設定エラーとせず、受理して警告する経過措置を置く。CLI の旧 flag（`--path`）も alias として残すか、移行先を示すエラーにする。

### 3.6 選択肢の比較

| 案 | 内容 | 判定 |
|---|---|---|
| A 現行 | reset＋再 push による全量置換 | 却下。P1 違反、prod では reset 自体が実行不能、原データ喪失のリスク、費用が総量に比例する |
| B メタデータ一括変換 | registry 書換＋索引再 PUT＋manifest 書換 | 却下。manifest は DEEP_ARCHIVE 上の不変履歴であり、取得と再アップロードを伴う履歴の書き換えになる。変換イベント自体が残り、次の改名でも同じ作業が再発する（registry の任意変換のみ、案 C の補助として残す） |
| C 読取互換＋遅延正規化 | 読取側で旧形式を全て受理し、書込のついでに自然に新形式へ寄せる | **推奨**。移行イベントが消え、費用は reader の adapter 実装のみ。再発しない |
| D 二重書込の移行期間 | 一定期間、旧新両形式を書き分ける | 却下。単一利用者の道具に対して過剰な機構である |

### 3.7 実装範囲（本設計の承認後の次段）

本設計のレビュー承認後、次の範囲を実装として tm へ起票する。

- reader 互換の実装: registry file_write・索引 entry・manifest file record の alias と版数受理、版数検査の改修（2.4 の一律失敗の解消を含む）。
- fixture の整備と条件書の追加（3.3 の保存形式 fixture テスト）。
- 文書の書換: changelog（unreleased）の移行手順、usage_backup.md の該当節（索引再構築・災害時手順）、`src/registry.rs` の前提コメント、dev_backup.md の正本参照の記述。
- config 旧 key・CLI 旧 flag の経過措置（3.5 の推奨事項。採否は実装時に判断する）。
